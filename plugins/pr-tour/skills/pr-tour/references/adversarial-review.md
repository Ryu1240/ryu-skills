# 敵対的レビューの並走（Phase 1-4 で起動、Phase 4-6・5 で取り込む）

> ツアーは「ここが何をしている場所か」を伝える。code-review は「ここで何が壊れ得るか」を探す。
> 別々に読むと、読み手は指摘を受けたときに該当箇所の文脈を思い出し直すことになる。
> そこで発火時に code-review をバックグラウンドで走らせ、届いた指摘を該当ステップの解説に添える。
> ツアー自身は判定しない。指摘は必ず「code-review の指摘」と出典を付け、実測で確かめるまで仮説として扱う。

## 0. 使える code-review かを見分ける（起動の前に必ず）

このツアーが前提にしているのは、effort レベル（`low` / `medium` / `high` …）と `--comment` / `--fix` フラグを受け取り、**結果を手元に返す** `code-review` スキルである。配布先の環境にそれがあるとは限らず、**同じ名前で別物が入っていることもある**。公式マーケットプレースの `code-review` プラグインは、PR 番号を受けて `gh pr comment` で GitHub にレビューコメントを**投稿する**。ツアーの途中でこちらが起動すると、解説のつもりで PR に公開コメントが付く。

- 利用可能なスキル一覧の `code-review` の説明文が、effort レベルと `--comment` / `--fix` に触れている → 起動する
- それ以外（名前が無い、説明が「Code review a pull request」だけ、`code-review:code-review` のようにプラグイン名前空間付きでしか無い、判別できない）→ **起動しない**。プランの「敵対的レビュー」行に「併走なし（理由）」と書いてツアーを続ける

迷ったら起動しない側に倒す。レビューが無くてもツアーは成立するが、誤って投稿されたコメントは取り消しても通知が残る。

## 1. 起動（Phase 1-4）

条件: `--no-review` が無く、0 の見分けを通った。level は既定 **medium**、`--review-level=<low|medium|high|xhigh|max>` で変える。

既定を medium にしているのは、ツアーの進行を止めない範囲で確度の高い指摘だけを拾うため。high 以上は見る範囲が広がるかわりに時間がかかり（大きな PR では 1 時間を超えることがある）、確度の低い指摘も混ざる。差分が大きい PR や、リリース前の最終確認では上げる。

**level は必ず明示して渡す。** 省略すると code-review はそのセッションで最後に使った level を引き継ぐので、実行ごとに深さが変わってしまう。

**対象はできるだけ head のブランチ名で渡す**（`feat/cancel-order medium`）。PR 番号だけを渡すと、code-review が `main...HEAD`、つまり**手元の作業ツリーのブランチの差分**をレビューしてしまうことがある。作業ツリーが head と違う（スタックド PR の後続ブランチに立っている等）と、隣の PR の変更まで混ざった結果が返る。どちらで渡しても、結果が届いたら 2 の 0 で対象範囲を確かめる。

`Agent` ツールを `subagent_type: general-purpose`、`run_in_background: true` で起こす。プロンプトの雛形:

```
<owner>/<repo> の PR #<番号>（head ブランチ <headRefName>）を敵対的にレビューし、結果をファイルに書いてください。

制約:
1. Skill ツールで `code-review` を引数 "<headRefName> <level>" で実行し、その手順に従う。`--comment` と `--fix` は付けない
2. 対象は refs/pr-tour/<id>/head（SHA <head_sha>）。読み取り専用 worktree <worktree path> があればそこを読む。checkout・stash・作業ツリーの変更は禁止
3. GitHub への書き込み（コメント、レビュー、ラベル）は一切しない。gh は読み取りだけ
4. 結果は <repo>/.claude/pr-tour/pr-<番号>-adversarial-review.md に書く。書式は下記。ReportFindings が使えても、このファイルが唯一の成果物
5. code-review が実際にレビューした範囲（base...head、またはファイル一覧）を結果ファイルの先頭に書く
6. 終わったら「件数、CONFIRMED / PLAUSIBLE の内訳、ファイルパス」だけを短く報告する

書式:
# PR #<番号> 敵対的レビュー結果（code-review <level>、起動 YYYY-MM-DD HH:MM）
- head_sha: <40 桁>
- reviewed_range: <code-review が見た範囲>
- 完了: YYYY-MM-DD HH:MM
| # | 判定 | 場所（file:line） | 要点（入力と状態、その結果） | 対応案 | 実測方法（ローカルで確かめる手順、無ければ「なし」） |
以下、報告枠に入らなかった候補を「低優先」として箇条書き。
```

起動したら、プランの「敵対的レビュー」行に「進行中（起動 HH:MM、level <level>）」と書き、**完了を待たずに Phase 2 以降を進める。** 完了通知はターンの途中で届く。サブエージェントの報告はユーザーには見えないので、内容はこちらから伝える。サブエージェントが GitHub に書き込んだ形跡があれば、黙って進めずユーザーに伝える。

## 2. 結果の対応付け（Phase 4-6、または届いたターンの冒頭）

0. **対象範囲を確かめる。** 結果ファイルの `reviewed_range` がツアーの `base...head` と一致するか見る。違ったら、ツアーの差分に含まれない指摘はステップに配らない（「この PR の指摘」として出すと嘘になる）。隣接 PR に当たる指摘は完了時に「このツアーの範囲外」として分けて出し、範囲がずれていた事実も 1 行伝える
1. 指摘の `file` を、プランの各ステップの「見る場所」と突き合わせ、**その file を含む最初のステップ**に付ける。ステップの「指摘」行に `🔍 #<n> <判定> <file:line> <要点の見出し>` の形で書く
2. どのステップにも無い file の指摘は補足ステップへ
3. リポジトリ外との整合（相手側サービスの関数名・キュー名・ペイロードの形との不一致）は「完了」の振り返りへ
4. プランの「未確認・食い違い」に同じ内容があれば、そちらに `🔍 #n と同じ` を添えて統合する。ユーザーが既にレビューコメントとして残した論点と重なるものは、その旨を書く（二重投稿を避ける材料になる）
5. HTML 側は `plan-step.py --findings` でステップの `<details>` に載せ、`__FINDINGS__` の表に全件を載せる

結果に判定（CONFIRMED / PLAUSIBLE）が付いていないこともある。その場合は判定を推測で書かず、最初に指摘を伝えるステップで「このレビュー結果には判定が付いていない」と一言伝える。

## 3. ステップでの伝え方（Phase 5-3「敵対的レビューの指摘」）

1 件ずつ、次の順で短く。

1. **何が起きるか**: どんな入力・状態で、何が壊れるか（例「返金 API がタイムアウトすると、注文は `cancelled` に進むが返金は行われない」）
2. **根拠**: `file:line`。**伝える前に自分でその行を Read する。** code-review の行番号が head と食い違うことがある
3. **判定**: code-review の報告のまま（CONFIRMED / PLAUSIBLE）。PLAUSIBLE は「仮説」と言い添える
4. **対応案**: code-review の案をそのまま。ツアー側で別案を足すときは「別案」と分ける
5. **実測できるか**: `references/verification.md` の範囲で確かめられるなら、そのステップで確かめるかをユーザーに選ばせる。実測すると撤回される指摘は珍しくない。結果（確定 / 撤回）は結果ファイルの該当行に追記する

伝え方の注意:

- 指摘は文脈（「ここは何をしている場所か」「変更点」）の後に置く。先に出すと、読み手は何が変わったかを掴む前に欠陥の話を聞くことになる
- 修正方針の議論には深入りしない。直したくなったら、ツアーの後で effort 付きの `code-review` に `--fix` を付けて渡せると案内して先へ進む（0 の見分けで別物と判断した環境では案内しない）
- 質問ログには「Step k で: 🔍 #n について〜」の形で残す。レビューコメントの材料になる
- ユーザーが「それは意図どおり」「対象外」と判断した指摘は、結果ファイルに「除外（理由）」を追記して以後は出さない

## 4. 届くタイミングごとの扱い

| タイミング | 扱い |
|---|---|
| Phase 4 の前に届いた | 対応付けてプランに載せ、承認メッセージで「完了 N 件」と示す |
| Phase 5 の途中で届いた | そのターンの冒頭で対応付け、**既に通過したステップの指摘は「戻り: Step m の <file> について」と 1 件ずつ短く伝える。** 黙って飛ばさない。現在以降のステップの指摘は到達時に伝える |
| 完了までに届かなかった | 「完了」の 3 で「レビューは未着、届いたら別途伝える」と書く。黙って省くと、読み手は指摘ゼロだったと受け取る。完了通知が来たら一覧を渡す |
| 再開時 | 結果ファイル先頭の `head_sha` が現在の head と一致するときだけ再利用する。違えば起動し直す |

「併走なし」「未着」「指摘なし」は読み手にとって意味が違うので、書き分ける。

## 5. やってはいけないこと

1. サブエージェントに GitHub への書き込みを許す。指摘の投稿は Phase 6（`review-handoff.md`）でユーザーの承認を経て行う
2. 指摘を出典なしに解説へ溶かす。「code-review の指摘」と分かる形を保つ
3. PLAUSIBLE を確定のように伝える
4. 完了を待ってツアーを止める。レビューは並走であって前提ではない
5. 併走なしのときに、代わりに自分で粗探しを始める。ツアーが止まる。歩く中で明らかな破綻に気づいた場合だけ 1 行添える
