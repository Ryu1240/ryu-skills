# エントリーポイントの見つけ方と辿り方（Phase 3 で読む）

> 差分に含まれるファイルから「処理の起点」まで外側へ辿るための地図。
> ここに書いてあるのはどのリポジトリにも通じる型だけ。リポジトリ固有の起点（どのファイルがルーティングか、どこが composition root か）は、Phase 3 の最初にそのリポジトリの文書とコードから組み立てる。

## 0. このリポジトリの起点カタログを作る（最初に 1 回）

決め打ちの表は持たない。リポジトリごとに構成が違い、外れた表は誤った起点に誘導するからだ。代わりに、ツアーの最初に次の順で読み、プランの「リポジトリの約束事」と、この節の 1 の表を自分用に埋める。

1. `CLAUDE.md` / `AGENTS.md` / `README` / `CONTRIBUTING.md` / `ARCHITECTURE*.md` / `docs/`（ADR があれば一覧）— レイヤーの分担、依存ルール、デプロイ単位
2. パッケージやモジュールのドキュメントコメント（`doc.go`、パッケージ冒頭のコメント、`__init__.py` の docstring）— `CLAUDE.md` が無いリポジトリでは規約がここにしか無いことがよくある
3. ビルド・起動の定義（`package.json` の `scripts`、`Makefile`、`Procfile`、`Dockerfile` の `CMD`、`main` を持つファイル）— プロセスが何から始まるか
4. CI の定義（`.github/workflows/` など）— PR で何が検査されるか
5. lint・依存ルールの設定 — 機械で強制されている約束事

リポジトリの文書が層の名前や依存の向きを決めているなら、それを使って起点を語る。一般論（「普通はこう書く」）と混ぜない。

## 1. 起点の型

エントリーポイント = 外部からの刺激がこのシステムに入る最初の一点。

| 種別 | 典型的な起点 | 起点だと分かる目印 |
|---|---|---|
| HTTP API | ルータ定義・ルートテーブル → ミドルウェア → ハンドラ | パスと HTTP メソッドがハンドラに結ばれている箇所 |
| CLI | `main()` / コマンド定義 | 引数パーサにサブコマンドが登録されている箇所 |
| フロント（SPA / SSR） | ルート定義・ページコンポーネント → データ取得 | ファイルベースルーティングのディレクトリ、ルータの設定 |
| UI イベント | イベントハンドラ（onSubmit / onClick / gesture）→ 状態更新 → 再描画 | テンプレート・JSX のイベント属性 |
| モバイル | アプリ起動 / ディープリンク / 画面遷移 → ViewModel・Presenter | Manifest / plist、ナビゲーショングラフ |
| ワーカー / ジョブ | ジョブの登録側（enqueue）と、ワーカーのディスパッチ | キュー名・ジョブクラス名で両側を結ぶ |
| 外部イベント | webhook / メッセージ購読 / cron・スケジューラのハンドラ登録 | 購読設定、スケジュール定義、IaC のトリガー |
| ライブラリ | 公開 API（エクスポートされた関数・型） | パッケージのエントリ（`index`、`lib.rs`、`__init__`） |
| スキーマ変更 | マイグレーションの適用と、その表を触る最初のクエリ | マイグレーションのファイル名と、モデル・リポジトリの参照 |
| インフラ（IaC） | スタック・モジュールのエントリ → 環境ごとの設定 → リソース | IaC のアプリ定義、環境別の設定ファイル |
| CI / デプロイ | ワークフローのトリガー（`pull_request` / `push` / 手動） | `on:` や相当する定義 |

## 2. 到達の判定

判定は「差分の外から差分へ到達できるか」で行い、根拠を file:line で示す。到達の形は 3 つ。

1. 直接呼び出し — 非テストコードからの参照が Grep で見つかる
2. フレームワークの規約 — ファイルベースルーティング、`resources` のようなルート DSL、Manifest 登録、DI コンテナのオートワイヤ、デコレータ・アノテーション。この場合は規約の根拠（設定ファイル・登録箇所）を起点にする
3. どちらも無い → 到達できない（断線）

Grep だけで判定すると、規約で結線されるフレームワークで必ず誤判定する。誰も import していないのに、実際は繋がっている。

到達できない差分は、まずプロセスの本当の起点（サーバの起動と配線、アプリのエントリ、ルート登録）を見てそこに今回の差分が居ないことを確認し、差分のうち外から参照される（予定の）公開面（インターフェース / 型 / export された関数 / コンポーネントの props / スキーマ）から、依存の向きに沿って内側へ降りる順でステップを組む。経路が途中まで繋がり、その先の差分がまだ誰からも呼ばれていない混在形も普通にある。繋がっている区間は流れ順に歩き、届いていない差分は「ここから先はこの PR では呼ばれていない」と明示した先に置く。存在しない経路を捏造して線を繋がない。

## 3. 差分の種類ごとの辿り方

### 3-1. コア（サービス・ユースケース・ドメイン）が変わった

1. 上へ: 変更された公開関数・メソッド名を、ハンドラ・ジョブ・CLI のディレクトリで Grep する。DI や composition root で実装が組み立てられている場合は、そこを経由して起点に着く
2. 横へ: そのコアが要求するインターフェース（ポート、リポジトリの型）が変わったら、それを実装する側と、それを注入する側の両方が文脈ファイル
3. 下へ: ドメインの型・関数。依存されている数が多いほど影響範囲が広いので、参照数を件数で示す

### 3-2. 外部連携（アダプター・クライアント・ゲートウェイ）が変わった

1. 上へ: 実装しているインターフェースの型名で Grep し、それを使うコアへ。複数実装（本番 / テスト用 / デモ用）があるものは、本番でどれが選ばれるかを composition root で確定させる
2. 外部 API の呼び出し形が変わるなら、権限（IAM ポリシー、API スコープ、シークレット）の定義も文脈に入る

### 3-3. ハンドラ・コントローラ・ジョブが変わった

1. 上へ: ルート定義・ジョブ登録・IaC のトリガー定義を Grep し、どのパス・どのキュー・どのスケジュールで動くかを確定させる
2. 入口の前段（ミドルウェア、認証・認可、入力検証）を通過点として見せる。差分に無くても、入力がどう整形されて届くかが分かる

### 3-4. 契約（API スキーマ・メッセージの型・共有の型定義）が変わった

1. 送る側と受ける側の両方を文脈に加える。片方しか差分に無いなら、それ自体が重要な事実
2. 生成コード（OpenAPI クライアント、protobuf、ORM のクライアント）は逐行解説せず、「この定義から何が生成され、どこで使われるか」だけ示す

### 3-5. スキーマ・マイグレーションが変わった

1. マイグレーションの内容（追加・変更・削除される列と制約）と、その表を触るモデル・リポジトリ・クエリを結ぶ
2. 既存データへの影響（デフォルト値、NULL 許容、インデックス作成のロック）はコードから読める範囲で事実として書く

### 3-6. 設定・環境変数が変わった

1. 値を定義する側（設定ファイル、IaC の環境変数、`.env.example`）と、読み出す側（`process.env`、`os.Getenv`、設定クラス）を対にして見せる

### 3-7. インフラ（IaC）が変わった

1. アプリ・スタックのエントリ → 環境ごとの設定 → 該当リソースの順で位置づける
2. 権限の変更は「誰が（Principal）」「何を（Action）」「どれに（Resource）」の 3 点で読む
3. 合成・plan のテスト（テンプレートのスナップショット、`hasResourceProperties` 相当）があれば、変更したリソースのプロパティを固定しているかを結びつける

### 3-8. CI・ワークフローが変わった

1. トリガーと権限を最初に見せる。デプロイ系は認証の仕組み（OIDC の信頼条件など）とつながる

### 3-9. 起点がリポジトリ外にある

差分に外部のサービス名・関数名・キュー名・アカウント ID・ペイロードの形が出てきたら、相手側の PR やリポジトリをユーザーに聞き、名前・リージョン・アカウント・ペイロードの形を突き合わせる。片側だけ読んでも見えない不一致は、両方読むと一目で分かることが多い。

### 3-10. テストが変わった、または追加された

1. テストの置き場所の慣習（実装と同じディレクトリか、`tests/` `spec/` に鏡像で置くか）をリポジトリから読み取り、テストファイルと実装ファイルを結ぶ
2. `describe` / `context` / `it`（またはテスト関数名・サブテスト名）の構造を読み、各ケースが「どのファイルのどのメソッド・分岐・条件」を固定しているかを特定する
3. 既存テストの期待値が反転していたら、それ自体が仕様変更の証拠なので拾う
4. テストの前提（fixture・factory の状態、モックの戻り値、テナントの切り替え）が PR 説明に無い条件を明かしていたら、該当ステップの「なぜ」の材料にする
5. テストが無い変更は「テストなし」として表に残す。判定はしない

### 3-11. ドキュメント・ADR が変わった

1. 起点ではないが、「この PR がどの決定を実装しているか」を示す。PR 説明が設計文書を指していれば、Step 1 の前に「なぜ」の材料として読む

## 4. 起点が見つからないときの判断

1. 呼び出し元が 0 件なら、未使用コードの追加か、DI・登録の漏れか、規約による結線を疑う。規約の根拠（ルートの登録、デコレータ）を探し直す
2. 呼び出し元が多すぎるなら、PR 説明・コミットメッセージ・設計文書・テストの `describe` から作者が意識している経路を本流にし、他は補足ステップに件数で示す
3. それでも決まらなければ、プランに「起点候補が複数あるためユーザーに確認」と書き、Phase 4 の承認時に聞く。推測で 1 本に決めない

## 5. 実行順と依存順がずれるとき

流れの順に歩いていると、後のステップで足された値や型を、前のステップがすでに使っている場面に出会う。矛盾ではなく、PR が「先に使う側を書き、後から供給側を足した」ことの現れで、フルスタックの PR では頻繁に起きる（画面側が使うフィールドを、最後にサーバのレスポンスへ追加する等）。

1. 前のステップでは、その値がこの PR で足されたものだとその場で明記し、供給元のステップ番号を指す（「この `discountId` は Step 6 で追加された値」）
2. 供給元のステップに着いたら回収する（「Step 2 の判定が成立するのは、この 1 行のおかげ」）
3. 図では、戻り矢印のラベルに書く。図の外の注記に逃がさない

この往復は、その PR で一番説明が要る場所であることが多い。差分を上から順に読んだ人が必ず取りこぼすのが、まさにこの依存だから。
