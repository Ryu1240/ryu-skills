# レビューコメントへの橋渡し（Phase 6、任意）

> ツアーの質問ログと未確認事項には、レビューコメントの材料が溜まる。ユーザーが「レビューコメントにしたい」
> 「下書きを作って」と言ったら、この手順で下書きを作り、投稿はユーザーの承認を得てから行う（投稿者はユーザー本人なので）。
> 判定は code-review の役割なので、ここでは「ツアーで見つかった事実と対応案」と「並走した code-review の指摘のうち実測で確定したもの」を整える。

## 1. 材料を集める

ツアーと同じセッションのまま続けるのが基本。会話に残っているやり取り（ユーザーが論点をどう受け止めたか、見送った論点とその理由）も材料になる。プランファイルは、compact 後や別セッションで始めたときに材料を取り戻すための記録として使う。

1. プランの「質問ログ」「未確認・食い違い」から、ユーザーが「レビューポイントとして残す」と言ったもの、または「実測で確定した事実とコードの食い違い」を拾う。「敵対的レビューの指摘」表からは、状態が「実測で確定」のものだけを候補にし、PLAUSIBLE のままのものは「未実測」と明示してユーザーに載せるかを聞く
2. 1 論点 = 1 コメント。同じ根から出た複数の症状（例: README の記述 3 箇所）は 1 コメントに束ね、根が同じ実装欠落があれば同じコメントに書く
3. 各論点に「対象ファイル:行」を付ける。インラインコメントは diff 上に存在する行にしか付けられない

## 2. 文体を本人に合わせる

投稿者はユーザー本人なので、本人の過去コメントと文体が揃っている必要がある。

```bash
gh api "repos/<owner>/<repo>/pulls/comments?sort=created&direction=desc&per_page=100&page=1" \
  --jq '.[] | select(.user.login=="<login>") | {pr: (.pull_request_url|split("/")|last), body}'
```

2〜3 ページ（200〜300 件）を読み、次を観察してから書く。観察結果は人とリポジトリごとに違うので、決め打ちしない。

- 文末の形（です・ます / 常体 / 感嘆符の有無）と、断定の強さ
- 提案と依頼の言い回し（疑問形で投げるか、依頼形で書くか）
- 判断を相手に委ねるときの書き方
- 根拠の示し方（実際に試した結果を書くか、コードの行を引くか）
- 実装者への配慮の一言があるか
- バッジ（must / nits など）や脚注を使うか。使っていて、かつ求められたときだけ付ける

ユーザーから「長い」「端的に」と言われたら、各コメントを「指摘 2〜3 文 + 対応案」に縮める。背景説明はチャット側に残せばよい。

## 3. 下書きを保存する

`.claude/pr-tour/pr-<番号>-review-draft.md` に、総評（PR 全体）と各コメント（対象・本文）を書く。投稿前にユーザーに見せて、文言と温度感の合意を取る。

## 4. Pending review として PR に置く

GitHub の Pending review は本人だけに見える下書きで、`event` を付けずに作ると PENDING になる。

```bash
gh api -X POST repos/<owner>/<repo>/pulls/<n>/reviews --input payload.json --jq '{id, state, html_url}'
```

payload は `{"commit_id": "<head sha>", "body": "<総評>", "comments": [{"path", "line", "side": "RIGHT", "body"}]}`。

制約と注意:

1. Pending review は 1 人につき 1 つ。既存があれば作成に失敗する
2. 削除して作り直す前に、API で本文とコメントを取得し、ローカルの下書きと比べる。ユーザーが GitHub 上で編集している可能性があり、削除するとその編集が失われる。差分があれば、その編集を新版に取り込むか、削除せず個別コメントを `PATCH /repos/<owner>/<repo>/pulls/comments/<id>` で更新する
3. 状態は毎回確認する。`gh api repos/<owner>/<repo>/pulls/<n>/reviews/<id> --jq .state` が `COMMENTED` / `APPROVED` / `CHANGES_REQUESTED` なら既に Submit 済みで、以降の追加は即時公開になる
4. Submit 済みのレビューには API でコメントを追加できない。追加は `POST /pulls/<n>/comments` の単発コメントになり、投稿時点で公開される。その旨を伝えて、ユーザーの明示的な OK を得てから投稿する
5. 本文で他リポジトリの PR を参照すると、「そちらに投稿する」と誤解されることがある。投稿先を明示する

## 5. 記録

下書きファイルの先頭に、Pending の ID、Submit の有無と時刻、単発投稿したコメントの ID を残す。中断後や compact 後に再開したときも二重投稿を避けられる。
