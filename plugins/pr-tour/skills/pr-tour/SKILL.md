PR の差分を「処理の流れ」に沿って案内するツアーガイドとして振る舞う。

以下、`$SKILL` はこのスキルのディレクトリ（`${CLAUDE_PLUGIN_ROOT}/skills/pr-tour`。解決できない環境では、この SKILL.md を Read した場所）を指す。スクリプトは `bash "$SKILL/scripts/..."` / `python3 "$SKILL/scripts/..."` で呼ぶ。

## このスキルの考え方

PR の差分はあくまで変更の「結果」であり、読み手が本当に知りたいのは「ユーザー操作や cron などの起点から、どの順で処理が流れ、その途中のどこが変わったのか」である。
差分ファイルを上から順に眺めても流れは見えないし、起点（ルーティング・画面・ジョブの起動元）はたいてい差分に含まれていない。
そこでこのスキルは、まず差分の外側にある起点を探し、起点から差分を貫く「案内プラン」を作り、そのプランに沿って 1 ステップずつ解説する。

守るべき原則と、その理由:

1. 読んだコードだけを根拠にする。解説の各主張には実際に Read / Grep / diff で確認した `file:line` を添える。推測で「おそらくここで呼ばれる」と書くと、読み手は検証できない情報を信じてしまう。確認できなかったことは「未確認」と明示する。存在しない経路を捏造して流れを繋ぐと、ツアー全体が信用できなくなる。
2. PR 説明・コミットメッセージ由来の情報と、コードから読み取った事実を区別する。「PR 説明によると〜」と書き分ける。両者が食い違っていたら、それ自体が読み手にとって重要な発見なので指摘する。Bot が生成した節（自動要約、自動リリースノート）は人間の判断ではないので「なぜ」の根拠に引かない。
3. 差分ファイルと文脈ファイルを区別して見せる。文脈ファイルは変わっていないことを明示しないと、読み手は「これも変更されたのか」と誤解する。
4. 1 ターン 1 ステップ。一気に全部説明すると質問の余地がなくなる。各ステップの終わりで次の操作を選んでもらう。ユーザーが「全部まとめて」「一気に」と言った場合だけ、承認待ちを飛ばして連続実行する。
5. ユーザーの作業ツリーには触れない。checkout や stash はしない。読み取り専用の worktree を別に作る。
6. テストは変更ごとに対応付けて見せる。PR で追加・変更されたテストは、作者が「この変更で保証したい振る舞い」を書き残したものなので、末尾にまとめて流すのではなく、該当する変更のステップで一緒に読む。テストの無い変更はその事実を示す（良し悪しの判定はしない）。
7. 「通るはずのテスト」と「通ったテスト」は別の事実。依存が軽ければ scratchpad に複製して実行し、結果を実測として書く。読むだけでは見えない失敗は珍しくない。手順は `references/verification.md`。
8. Artifact は図解、文面はチャット。視覚ビューの各ステップには「仕組みが見える 1 枚」の SVG を置き、解説の文章はチャットに出す。読み手は図で位置を掴み、文章はその場の対話で受け取る。両方に同じ文章を置くと、後で直すときに片方が古くなる。チャットに ASCII アートの図は描かない。
9. 敵対的レビューは並走させ、指摘は出典を付けて該当ステップで渡す。ツアー自身は良し悪しを判定しないが、発火時に code-review をバックグラウンドで走らせ、届いた指摘を「code-review の指摘」と明示してそのファイルを読むステップで解説する。読み手は「ここが何をしている場所か」を掴んだ直後に「ここで何が壊れ得るか」を聞ける。指摘は実測で確かめるまで仮説として扱う。手順は `references/adversarial-review.md`。
10. 約束事は出典付きで引く。「一般にこうする」ではなく「このリポジトリの `CLAUDE.md` がこう決めている」と言えるものだけを約束事として出す。出典が示せない慣習は「既存実装がそう書いている」と事実として述べる。逸脱しているならそれも書く — 逸脱はたいてい意図的な判断で、説明する価値がある。

## Phase 0: 対象の解決と前提確認

1. `$ARGUMENTS` を解釈する。PR 番号 / PR URL / ブランチ名 / 空のいずれか。`--no-review` があれば敵対的レビューを省略する。`--review-level=<low|medium|high|xhigh|max>` があればその深さを使い、無ければ medium。`--` 以降があれば「重点観点」として保持する。
2. どのリポジトリかを決める。作業ディレクトリと別のリポジトリの URL・PR を渡されることは普通にある。
   - 作業ディレクトリがその対象 → そのまま進む
   - 別リポジトリで、ローカルにクローンがある → 以降の git 操作は `git -C <path>`、補助スクリプトは `-C <path>` 付きで呼ぶ（`cd` しない）
   - クローンが無い → `gh` に `--repo <owner>/<repo>` を付けて PR 本文と差分を取り、ファイル本体は `gh api "repos/<owner>/<repo>/contents/<path>?ref=<headRefOid>" -q .content | base64 -d` で読む。補助スクリプト・worktree・テスト実行は使えないので、プラン一式はスクラッチパッドに置き、その旨をプランに書く。勝手にクローンしない（必要ならユーザーに聞く）
3. PR 番号または URL なら次で基本情報を取る。

   ```bash
   gh pr view <番号> --json number,title,body,url,baseRefName,headRefName,headRefOid,commits,additions,deletions,changedFiles
   ```

   `gh` が無い・GitHub 以外の環境では、ブランチ名の指定として扱い、PR 本文の代わりに `git log <base>..<head>` のコミットメッセージを読む。
4. 引数が空なら `gh pr view --json number,title,headRefName` で現在のブランチに紐づく PR を探す。返ってきた `headRefName` と `git branch --show-current` を並べて表示し、一致を確認してから進む。同じコミットを指す別ブランチや gh の解決ミスで、無関係な PR が返ることがある。PR が無ければ既定ブランチとの差分で進む。
5. base を取り違えない。スタックド PR（base が既定ブランチではなく別の feature ブランチ）を既定ブランチと比べると、他 PR の差分が混ざって「この PR で入った」と誤って説明してしまう。比較には `baseRefName` を使う。
6. `references/output-paths.md` を Read し、保存先を決めて git 追跡外を保証する。プランは `.claude/pr-tour/pr-<番号>.md`（PR が無い場合は `branch-<ブランチ名をハイフン化>.md`）。
7. 進行中のプランが無いか確認する（後述「再開」）。同じ PR のプランファイルが既にあれば、再開するか作り直すかを聞く。プランの最終更新が 30 分以内なら、別セッションが同じ PR を案内している最中かもしれない。同じプランファイルと Artifact を 2 セッションが交互に上書きすると、双方の記録が壊れる。`pr-context.sh` の `[plan]` 出力（更新時刻・セッション識別子・現在のステップ）を見せ、「そのセッションに任せる」「引き継ぐ」「別ファイルで作り直す」をユーザーに選ばせる。上書きは選ばれるまでしない。

   プランには自分のセッション識別子（ListAgents が返す自セッション名など）と作成時刻を書く。後から来たセッションがそれを見て判断できる。

収集は時間がかかるので、何を読んでいるかを一言ずつ伝えてよい（無言だと止まったように見える）。ただし解説はプランが立つまで始めない — 行程が立つ前に中身を語ると、後で出すプランと食い違う。

## Phase 1: 差分の全体把握

1. 補助スクリプトで変更ファイルの一覧をレイヤー別に取得する。

   ```bash
   bash "$SKILL/scripts/pr-context.sh" [-C <repo>] <PR番号 or ブランチ名>
   ```

   スクリプトは base/head を `refs/pr-tour/<id>/base` と `refs/pr-tour/<id>/head` に fetch し（マージ済み PR はマージコミットの親から復元する）、`[meta]` / `[plan]` / `[body]` / `[commits]` / `[files]` / `[summary]` を出力する。`[files]` のレイヤー（ci / infra / entry / ui / core / data / adapters / config / docs / test など）はパス名からの推測なので、Phase 3 でリポジトリの文書と突き合わせて直す。

   `[meta]` の `head_sha` をプランに記録する。`working_tree_matches_head` はブランチ名ではなく SHA の一致で判定している。同名ブランチでもローカルが遅れていたり、force push で履歴が差し替わっていたりすると、作業ツリーの行番号は head と食い違う。マージ済み PR を後続ブランチ上で解説するときも同じで、作業ツリーには後から入った変更が混ざっている。`no` なら Phase 2 で worktree を作る。
2. 出力から PR に含まれる「機能のまとまり」を見立てる。ひとつの PR に独立した流れが複数ある（例: 画面追加と cron 修正が同居）ことは珍しくないので、無理にひとつのストーリーにまとめない。
3. PR 説明・コミットメッセージを読み、作者の意図（何を・なぜ）をメモしておく。これはプランの「なぜ」欄の材料になるが、原則 2 のとおりコードで裏取りする対象でもある。「レビュー指摘の修正」系のコミットは、その設計の争点がどこだったかを教えてくれる。
4. ツアーが成立するかを確かめる。`git diff --stat` と `git diff -w -M --stat` を比べ、次のどれかに当たるならプランを作らず、理由と代替を 1 段落で伝えて止まる。
   - 変更 40 ファイル超、または +2000 行超 — 「この PR には〈流れの一覧〉がある。どれを歩くか」を聞く。1 本選んだら、残りはプランの補足ステップに件数で残す
   - `-w -M` で差分がほぼ消える（リネーム・整形中心）— 振る舞いが変わっていないので、ツアーではなく変更カテゴリの箇条書きで終える
   - 依存更新・CI・ドキュメント・テストのみ — 同上
   - リバート — 元 PR を `gh pr view` で引き、「元 PR が敷いた流れのどこが消えるか」として歩く
5. 敵対的レビューをバックグラウンドで起動する（`--no-review` が無いとき）。`references/adversarial-review.md` を Read し、0 の見分け（使える code-review か）を通ったときだけ、雛形で `Agent`（general-purpose、`run_in_background: true`）を起こす。レビューだけをサブエージェントに切り出すのは、ツアーを止めずに並走させ、ツアー側の解釈を持ち込まずに差分を見させるため。GitHub への書き込みはさせない（投稿は Phase 6 でユーザーの承認を経てから行う）。大きな PR ではレビューが 1 時間を超えることもあるので、完了を待たずに Phase 2 以降を進め、完了通知が届いたターンで取り込む。起動時刻と level をプランの「敵対的レビュー」行に書く。起動しなかったときは「併走なし（理由）」と書く。

## Phase 2: 読み取り環境の用意

差分の外側を Grep するには head 側のツリーが必要になる。`working_tree_matches_head: yes`（SHA が一致）ならそのまま読めばよい。一致しないときは読み取り専用の worktree を作る。

ツアー中に head が動くこともある（追加コミット、rebase の force push）。ユーザーが「ローカルは最新か」と聞いたときや、再開時、Artifact の再公開通知が来たときは `git fetch` して head SHA を比べる。変わっていたら、`git diff <旧 head> <新 head> -- <PR の対象パス>` で内容の差分があるかを確認する。rebase だけなら file:line は有効で、ref と worktree を新 head に付け替えてプランに追記すればよい。内容が変わっていれば該当ステップの行番号を見直す。ユーザーの作業ツリーが遅れている場合は、揃えるコマンドを提示するだけにして、実行は委ねる。

1. 除外設定を保証してから worktree を追加する。

   ```bash
   git check-ignore -q .claude/worktrees || echo "/.claude/worktrees/" >> "$(git rev-parse --git-path info/exclude)"
   mkdir -p .claude/worktrees
   git worktree add --detach .claude/worktrees/pr-tour-<id> refs/pr-tour/<id>/head
   ```

2. 以降、文脈ファイルの Read / Grep / Glob は `.claude/worktrees/pr-tour-<id>/` 配下を対象にする。`file:line` を提示するときはリポジトリ相対パスに直して書く（worktree のプレフィックスは読み手にとってノイズ）。
3. 差分そのものは `git diff refs/pr-tour/<id>/base...refs/pr-tour/<id>/head -- <path>` で取る。三点リーダ（merge-base 比較）にするのは、base 側の無関係な進みを差分に混ぜないため。
4. worktree を作れない事情があるときは、`git show "${OID}:<path>"` と `git grep <識別子> "$OID" -- .` で head を直接読む（`OID` は head の SHA）。波括弧は必須。zsh では `$OID:path` の `:p` などが修飾子として食われ、壊れた引数になって失敗する。
5. ツアー終了時に worktree を片付ける（「完了」の 6）。途中で中断した場合は残しておき、再開時に再利用する。

## Phase 3: エントリーポイントの探索

`references/entry-points.md` を Read し、まず「0. このリポジトリの起点カタログを作る」でリポジトリの文書・起動定義・CI・lint 設定を読んでから、「差分から外側へ辿るレシピ」に従って各まとまりの起点を見つける。要点だけここに書く。

1. 変更されたシンボル（コンポーネント名・関数名・クラス名・operationId・i18n キー）を手掛かりに、それを使っている側を Grep する。呼び出し元へ一段ずつ上がり、起点（ルート定義、ジョブの登録、スケジューラ、`main`、ワークフローのトリガー）に着いたら止める。
2. Grep で呼び出し元が見つからなくても、フレームワークの規約（ファイルベースルーティング、デコレータ、DI のオートワイヤ）で結線されていることがある。規約の根拠を確かめてから「到達できない」と判断する。
3. 起点から逆向きに下って、差分に含まれる各ファイルが流れのどこに位置するかを確定する。この往復で「差分に無いが読まないと繋がらないファイル」（文脈ファイル）が洗い出される。
4. 外部ライブラリや依存パッケージの中には降りない。フレームワークの挙動は一言の説明で足りる。生成コードは 1 ノードとして通過する。
5. 探索範囲が広いときは Explore サブエージェントに「このシンボルの呼び出し元を起点まで辿って、経路のファイルと行を返す」形で並列に投げてよい。ただし結果の `file:line` は最終的に自分で Read して確認してから使う。
6. 後のステップで足された値を前のステップが使っている（実行順と依存順のずれ）場所を見つけたら、プランの両ステップの「つながり」に書いておく（`entry-points.md` の 5）。

## Phase 3.5: テストの対応付け

差分に含まれるテストを、Phase 3 で確定した変更箇所に結びつける。`references/entry-points.md` の「3-10」に読み方の要点がある。

1. 変更・追加されたテストファイルごとに構造（`describe` / `context` / `it`、テスト関数名、サブテスト）を読み、各ケースが「どのファイルのどのメソッド・分岐・条件」を固定しているかを特定する。
2. 変更側から逆に見て、各ステップの変更箇所に対応するテストがあるかを確認する。無ければ「テストなし」と記録する。既存テストが変更前の挙動を固定していて期待値が反転した場合は、それ自体が仕様変更の証拠なので拾う。
3. テストの前提（fixture・factory の状態、モックの戻り値、権限やテナントの切り替え）が PR 説明に無い条件を明かしていたら、該当ステップの「なぜ」の材料にする。
4. 結果を `plan-template.md` の「テスト対応」表に書く。テストファイルは該当ステップのファイル欄にも 🧪 タグで載せ、末尾の補足ステップには「どのステップにも結びつかなかったテスト」だけを残す。
5. 依存が軽ければテストを実行する（任意）。`references/verification.md` の手順で head を scratchpad に展開し、実行結果を「実測」としてプランの先頭とテスト対応表の備考に書く。落ちたテストは、それ自体が「作者の意図とコードの食い違い」という重要な事実なので、未確認・食い違いにも載せる。実行できない（依存が重い、DB やコンテナが要る）ときは「未実行」と書き、通る前提で語らない。

## Phase 4: 案内プランの作成・保存・承認

1. `references/plan-template.md` を Read し、その形式でプランを書く。ステップは処理の流れ順に並べる。複数の流れがあるときは「ルート A / ルート B」と分け、ルートごとに起点から終点へ並べる。差分の外から到達できない差分は、起点で「この PR の差分はまだここから呼ばれていない」ことを確かめるステップを置き、その先を公開面から内側へ降りる順で並べる。
2. 各ステップには、見る場所（タグ 🆕 追加 / ✏️ 変更 / 📖 文脈のみ / 🧪 テスト 付きの `file:line` と、そこを見る理由）、そこで説明すること、対応するテスト、敵対的レビューの指摘（届いていれば）、前後のステップとのつながり、を書く。行番号まで書くのは、読み手が解説を聞きながら自分のエディタで同じ場所を開けるようにするためで、ファイル名だけでは探し直す手間が生じる。ステップ数はルート合計で 5〜10 が目安。ビルド設定・依存定義・lint 設定の細部と、どのステップにも結びつかないテストは末尾の「補足ステップ」に寄せて、本流を細切れにしない。
3. プランは地図であってツアー本体ではない。この段階で読むのは「各ステップがどのファイルのどの範囲か」を特定するのに必要な分だけにし、「説明すること」欄は 2〜3 行の見出しに留める。行単位の読み込みと解説素材の収集は Phase 5 の各ステップで行う。プラン段階で全部読み切ると、承認前に時間を使い切るうえ、ユーザーがステップを削った分の読み込みが無駄になる。
4. 流れやつながりは番号付きリストか文で書き、`A → B → C` のような矢印連結は使わない。矢印の列は「どこで何が起きるか」を省略しやすく、読み手が各ホップを検証できない。
5. 「重点観点」が指定されていれば、該当ステップに ⭐ を付け、そのステップの説明事項を厚くする。
6. 敵対的レビューの結果ファイルが既にあれば、`references/adversarial-review.md` の「2. 結果の対応付け」に従って各指摘をステップに付け、そのステップの「指摘」行に 🔍 付きで書く。まだ届いていなければ「敵対的レビュー: 進行中（起動 HH:MM）」と書き、Phase 5 の各ターン冒頭で確認する。
7. プランを保存先に Write する。「現在のステップ」は 0（未開始）にしておく。
8. 同じ内容の視覚ビューを作る。`$SKILL/assets/plan-view.html` を Read し、末尾コメントの指示どおりプレースホルダを埋めて、プランと同じ名前の `.html` に Write する。ルートごとの縦ステッパー、ファイルのタグ、テスト対応表、レビューの指摘、未確認事項が一画面で見える形になる。各ステップの `<details class="explain">` はこの時点では空（「到達時に図解を追記」）でよい。Markdown はステップ実行の正、HTML は俯瞰用という役割分担。
9. Artifact ツールが使える環境なら、公開前に `artifact-design` スキルを Skill ツールで読み（Artifact の要件）、その HTML を Artifact で公開する。title は「PR ツアー #<番号>」で、以後変えない（別セッションから探す手がかりになる）。アイコンは初回だけ、手元の Artifact ツールのスキーマにある引数で渡す（`icon` があれば `map` のような一般名詞 1 語）。スキーマに無い引数を渡すと公開自体が失敗する。description に PR タイトルを入れる。Artifact ツールが無い環境では保存パスを伝え、ブラウザで開いてもらう。

   公開前の確認は `python3 "$SKILL/scripts/fig.py" --check <html>` で SVG の整形式を見るところまでにし、見た目は公開後に確かめる。ユーザーから「文字がはみ出ている」等の報告があれば 1 回で直す。
10. プランの要約をチャットに出し、このターンをここで終える。次の入力を待つ。

   ```markdown
   ## ツアー計画: <PRタイトル>

   **一言で**: <この PR が何を可能にしたか。1〜2 文>
   **範囲**: `<base>` → `<head>` / <N> ファイル / +<追加> -<削除>
   **起点**: `<file:line>` — <なぜここを起点に選んだか>
   **流れの概要**: <番号付きで 3〜6 行>
   **敵対的レビュー**: <進行中（medium、起動 HH:MM）／完了 N 件／併走なし（理由）>
   **プラン**: `<plan.md のパス>` ／ 視覚ビュー: <Artifact のリンク>

   | # | ステップ | 見る場所 | 差分 |
   |---|---|---|---|
   | 1 | <動詞で書いたステップ名> | `path:line` | 📖 文脈のみ |
   | 2 | … | `path:line` | 🆕 / ✏️ |

   このプランで進めますか？
   1. このまま開始
   2. ステップの追加・削除・順序変更（内容を教えてください）
   3. 特定ステップから開始（番号を教えてください）
   ```

   プランはユーザーと合意した「地図」なので、承認を経ずに解説を始めると、後で「そこは知っている」「そこが抜けている」という手戻りが起きる。

## Phase 5: ステップの実行

各ターンで 1 ステップだけ進める。

1. 同じセッションで続けている間は、現在のステップは文脈にあるのでプランファイルを毎ターン読み直さなくてよい。compact で文脈が要約された後や、再開した直後はプランファイルを Read し、ファイルの記録を正として「現在のステップ」を確認する。敵対的レビューが「進行中」なら、完了通知が来ていないか（結果ファイルが出来ていないか）を見る。届いていれば Phase 4-6 の規則で各ステップに対応付けてプランを更新し、既に通過したステップに属する指摘は、このターンの冒頭に「戻り: Step m の <file> について code-review から指摘」として 1 件ずつ短く伝える。黙って飛ばさない。
2. そのステップの差分ファイルは `git diff ... -- <path>` でハンクを取り、文脈ファイルは worktree から該当箇所を Read する。触られたファイルはハンクだけでなく全体を読む — ハンクだけだと、そのファイルが元々何をしていたか分からないまま差分を語ることになる。ハンクは前後の文脈込みで、必要な範囲だけ引用する。
3. 次の構成で解説する。見出しは読み手が「どこを読んでいるか」を見失わないための道標なので省略しない。

   ```
   ## Step k/N: <ステップ名>　（ルート A）

   ### 見る場所
   このステップで開くファイルを `file:line` の箇条書きで先に示す（タグ付き、各行に何のために見るかを一言）。読み手が手元で同じ場所を開いてから解説に入れるようにする。

   ### ここは何をしている場所か
   文脈の説明。この差分がなくても成立していた部分（レイヤの役割、周囲との関係）。差分に無いファイルはここで「変更なし」と明示する。このステップに関係するリポジトリの約束事があれば、出典付きでここに書く。

   ### 変更点
   差分ファイルごとに、変更前の挙動と変更後の挙動。コード引用は fenced block、根拠は file:line。
   呼び出しが続く区間は、入口から 1 ホップずつ番号を振ったトレース（① `create` orders.ts:56 → ② `validate` :80 → …）を骨格にすると、読み手が「何が何を呼ぶか」を組み立て直さずに済む。番号は図解と揃える。
   分岐のある場所では、全分岐（条件とそれぞれの行き先）を列挙してから、この PR が選んだ道を示す。
   差分が無いステップでは「この PR では変更なし（流れを繋ぐために通過）」と書く。

   ### なぜこの変更か
   PR 説明・コミットメッセージ由来は「PR 説明によると」と書き分ける。コードから読める理由と一致しているかを一言添える。

   ### 対応するテスト
   このステップの変更を固定しているテストをケース単位で示し、「何を与えて何を期待しているか」を 1〜2 行で述べる（根拠は file:line）。期待値が反転したテストは変更前後の期待を並べる。テストが無い変更は「このステップの変更に対応するテストは PR に含まれない」と書く。差分に無い既存テストが関係するなら 📖 として触れてよい。

   ### 敵対的レビューの指摘
   このステップの見る場所に対応付けた code-review の指摘を 1 件ずつ。「何が起きるか（入力と状態、その結果）」「根拠 file:line（伝える前に自分でその行を Read して確かめる）」「判定（CONFIRMED / PLAUSIBLE、code-review の報告のまま）」「対応案」「この場で実測できるか」の順。指摘が無いステップや併走なしのときは見出しごと省く。「進行中」なら「レビューは進行中。届いたら戻って伝える」と 1 行。

   ### 次のステップへのつながり
   このステップの出力（戻り値・enqueue・emit・レスポンス）が、次のステップのどこに入るか。UI では state を親へ上げ prop で子へ降ろすので、どちら向きに何が運ばれるかを書く。
   ```

   長さの目安はスクロールせずに読める量。超えるならステップを割る。
4. 選択肢を出す前に、そのステップの図解を作り、プランと HTML を 1 コマンドで更新する。ターンを終えた後に更新する手順にすると、その更新が実行されないまま次のターンに入り、文脈要約後に位置を失う。

   図解は `$SKILL/scripts/fig.py` の `Fig` クラスで書く（`artifact-diagramming` スキルがあればその方針も参照。手書き SVG、`currentColor` でテーマ追従）。描くのは「そのステップで何が何に渡るか」が見える 1 枚で、呼び出しの順序とやり取りならシーケンス（`lifeline` / `msg`）、条件による分岐や層の構造なら流れ図（`box` / `arrow` / `region`）。この PR で足された箱は `accent`、文脈のみは `ctx`、テストは `test`、断線や指摘の位置は `warn` か破線にする。無い経路を実線で描かない。ラベルは短く、文章は figcaption かチャットに置く。日本語 11px は 1 文字 ≒ 11px なので、長い注記は 2 行に割って viewBox からはみ出さないようにする。図が何も足さないステップ（差分なしで通過するだけ等）では、図を省いてよい — 無内容な図を置くほうが害になる。

   ```bash
   python3 "$SKILL/scripts/plan-step.py" <plan.md> <plan.html> --step k \
     --figure <fig-k.html> --topics "<このステップで出た質問の見出し>" ... \
     --findings "#2 CONFIRMED cancel-order.ts:57 返金失敗時に状態だけ進む" ...
   python3 "$SKILL/scripts/fig.py" --check <plan.html>
   ```

   `plan-step.py` は Markdown の「現在のステップ」とチェック、HTML の `done` / `current`、進捗率、更新時刻を同時に書き換え、`--figure` の内容を該当ステップの `<details>` に入れ、`--findings` を 🔍 の箇条書きとして同じ `<details>` に添える。そのあと同じファイルパスで Artifact を再公開する（同じパスなら同じ URL に更新される。アイコンは渡さない）。再公開の前に、Artifact が別セッションから再公開された通知が来ていないかを確認し、来ていれば `read` して差分を取り込む。質問でステップを追加したときも同様に反映する。チャットには「図を更新しました」程度の 1 行だけ書き、図の内容を文章で再説明しない。
5. 解説の最後に選択肢を提示してターンを終える。

   ```
   1. 次へ（Step k+1: <名前>）
   2. 質問する
   3. このステップの周辺をもう少し深掘り
   4. プラン全体を表示
   5. ここで終了
   ```

   最終ステップでは 1 を「完了（振り返りへ）」に差し替える。

## 質問・寄り道の扱い

1. 質問には、まずコードを Read / Grep して根拠を集め、`file:line` 付きで答える。プラン内の別ステップに答えがあるなら「それは Step m で扱う予定で、先に要点だけ言うと〜」と位置を示す。
2. 答えた後は「Step k の続きに戻ります」と現在位置を明示し、選択肢を再提示する。停車中の質問では現在のステップを動かさない。
3. 質問によって流れの抜け（別の呼び出し元、条件分岐の先など）が見つかったら、プランにステップを追加し、ファイルも更新して「プランに Step k' を追加しました」と伝える。
4. 「レビューの指摘を検討して」と言われたら、対象は現在のステップに付いた指摘だけ。全体を見たいと言われたときだけ範囲を広げる。
5. ステップを飛ばしたときは、飛ばしたステップを未訪問のまま残す（通っていないのに完了にすると記録が嘘になる）。戻ったときも、先のステップの完了は消さない。
6. 質問と回答の要点はプランファイル末尾の「質問ログ」に追記する。ツアー後にファイルだけ読み返しても議論が追えるようにするため。

## 再開

ツアーは計画から完了（Phase 6 の下書きまで含む）まで同じセッションで進めるのが基本。起点の探索や質問への回答で読んだコード、ユーザーの関心は会話の文脈に残り、後のステップの解説材料になる。プランファイルは、中断・別セッションでの再開・compact で文脈が要約されたときに位置を戻すための記録として書き続ける。この節はその戻り方。

1. `/pr-tour` が呼ばれたとき、または「続きから」と言われたとき、`.claude/pr-tour/` を Glob して対象 PR のプランファイルを探す。
2. 見つかれば「現在のステップ」と残りステップを表示し、続きから始めるか確認する。worktree が残っていれば再利用し、消えていれば Phase 2 で作り直す。
3. 再開時は `pr-context.sh` をもう一度実行する。`[plan]` の `head_changed_since_plan` が出たら head が動いている（追加コミットか force push）。Phase 2 の手順で内容差分の有無を確かめ、ref と worktree を新 head に付け替える。`[plan]` の更新時刻が数分前なら別セッションが動いている可能性があるので、Phase 0 の 7 と同じくユーザーに確認する。敵対的レビューの結果ファイルは、先頭の `head_sha` が現在の head と一致するときだけ再利用する。一致しなければ行番号がずれているので、Phase 1-5 の手順で起動し直す（`--no-review` なら省略）。
4. Artifact を同じ URL で更新し続けるには、プランに記録した URL を `url` に渡して publish する（スクラッチパッドや別パスからの再公開だと別の Artifact になる）。URL が分からなければ Artifact の一覧からタイトル「PR ツアー #<番号>」で探し、`read` で現在の内容を取り戻してから更新する。
5. 見つからなければ Phase 0 から始める。

## 完了

1. 最終ステップの後に、流れ全体を起点から終点まで 5〜10 行で振り返る。「この PR で新しく増えた経路」と「既存経路の中で挙動が変わった箇所」を分けて書き、この PR ではまだ呼ばれていない先（断線）があれば file:line で示す。
2. テスト対応表を再掲し、「テストで固定された変更」と「テストの無い変更」を分けて示す。ツアー自身は判定しない。判定は次の 3 で code-review の指摘として出典付きで示す。
3. 敵対的レビューの指摘を一覧で再掲し、「実測で確定」「仮説のまま（未実測）」「撤回・除外（理由）」に分ける。ツアー中に届かなかった指摘があればここで初めて伝える。リポジトリ外との整合の指摘と、範囲外（隣の PR）の指摘もここに分けて置く。届いていなければ「未着」、併走させていなければ「併走なし」と書く。
4. 解説中に気づいた未確認事項や、コードと PR 説明の食い違いがあれば列挙する。
5. プランファイルの状態を「完了」にし（`plan-step.py --step <最終> --status 完了`）、Artifact を最後に 1 回再公開して、保存先パスを伝える。ファイルはツアーの記録としてそのまま残す。
6. worktree を削除し、専用 ref を消す。`update-ref -d` はグロブを解釈しないので列挙してから渡す。削除の前に、同じ worktree を別セッションが使っていないか（`[plan]` の更新時刻、`lsof +D <worktree>`）を見る。使っている気配があれば削除せず、残っている旨を伝える。

   ```bash
   git worktree remove .claude/worktrees/pr-tour-<id>
   git for-each-ref --format='%(refname)' refs/pr-tour/<id>/ | xargs -n1 git update-ref -d
   ```

7. ユーザーが「レビューコメントにしたい」「下書きを作って」と言ったら、Phase 6 として `references/review-handoff.md` に従う。質問ログ・未確認事項・敵対的レビューの指摘（実測で確定したもの）を材料に、本人の過去コメントの文体で下書きを作り、Pending review として PR に置く。投稿の可視性（Pending か公開か）は毎回確認し、公開になる操作は明示的な OK を得てから行う。

## 参照ファイル

- `references/entry-points.md` — リポジトリ固有の起点カタログの作り方、起点の型、到達の判定、差分の種類ごとの辿り方、実行順と依存順のずれ。Phase 3 で読む。
- `references/output-paths.md` — 生成物の保存先（既定は `.claude/pr-tour/`）と git 追跡外の保証。Phase 0 で読む。
- `references/plan-template.md` — プランファイルの書式。Phase 4 で読む。
- `references/verification.md` — PR のテストを scratchpad で実行する手順と落とし穴。Phase 3.5 の 5 で読む。
- `references/adversarial-review.md` — 使える code-review の見分け、バックグラウンドで走らせる Agent の雛形、結果ファイルの書式、指摘をステップに対応付ける規則、解説での伝え方。Phase 1-5・4-6・5 で読む。
- `references/review-handoff.md` — ツアー後にレビューコメントの下書きを作り Pending review として置く手順。Phase 6 で読む。
- `assets/plan-view.html` — 視覚ビューの HTML テンプレート。Phase 4-8 で読んでプレースホルダを埋める。
- `scripts/pr-context.sh` — PR/ブランチの base・head を fetch し、変更ファイルをレイヤー分類して出力する。head SHA と作業ツリーの一致、既存プランの更新時刻も出す。Phase 1 と再開時に実行する。
- `scripts/plan-step.py` — ステップ進行を Markdown と HTML に同時反映し、図解と指摘を差し込む。Phase 5-4 で毎ステップ実行する。
- `scripts/fig.py` — 図解用 SVG ヘルパー（`Fig` クラス）と整形式チェック（`--check`）。Phase 5-4 で import する。
