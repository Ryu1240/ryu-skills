# PR ツアーガイド

## 狙い

差分をファイル単位で舐めない。**実行が流れる順に歩き、各駅で「元からあったもの」と「今回の差分」を分けて示す**。読み手は初見だと想定する。

役割分担は固定:

- **文章はチャット** — 解説・引用・file:line
- **図解はアーティファクト** — 1枚だけ作り、ステップごとに同じURLへ再publishして現在地を進める。中身は **処理の流れを表す本物の図**（シーケンス図・フローチャート等）であって、装飾したリストではない

チャットにASCIIアートの図を描かない。両方に描くと必ずズレる。

## 全体の流れ

| Phase | やること | 発言 |
|---|---|---|
| 0. 収集 | PRと周辺コードを読み、敵対的レビューを起動し、ツアーが成立するか判断する | 進捗を短く伝えるだけ（解説はまだしない） |
| 1. 計画提示 | 行程表をチャットに出し、全体マップを公開し、承認を待つ | する → 止まる |
| 2. ステップ実行 | 1ステップ = 1ターン。解説 → マップ更新 → 止まる | する → 止まる |
| 3. 締め | 振り返りと、繋がっていない先・残る論点 | する |

ユーザーが「全部まとめて」「一気に」と言った場合だけ、承認待ちを飛ばして連続実行する（その場合 publish は最終状態で1回だけ）。

## Phase 0: 収集

### 対象の特定

**まずどのリポジトリかを決める。** 作業ディレクトリと別のリポジトリのURL・PRを渡されることは普通にある。

- 作業ディレクトリがその対象 → そのまま進む
- 別リポジトリで、ローカルにクローンがある → `git -C <path>` で読む（`cd` しない）
- クローンが無い → `gh` に `--repo <owner>/<repo>` を付けてPR本文と差分を取り、ファイル本体は `gh api repos/<owner>/<repo>/contents/<path>?ref=<sha> -q .content | base64 -d` で読む。勝手にクローンしない（必要ならユーザーに聞く）

| 言われ方 | 取り方 |
|---|---|
| PR番号 / PRのURL | `gh pr view <N> --json title,body,baseRefName,headRefName,headRefOid,files` と `gh pr diff <N>` |
| ブランチ名 | `git diff <base>...<head>`（三点。merge-base からの差分になる） |
| 指定なし | 現在のブランチ。`gh pr view --json ...` が通ればそのPR、通らなければ main との差分 |

**base を取り違えない。** スタックドPR（baseが main ではなく別のfeatureブランチ）を main と比べると、他PRの差分が混ざって「このPRで入った」と誤って説明してしまう。`baseRefName` を必ず確認する。

**読むリビジョンを固定する。** 差分の外のコード（ファイル全体・呼び出し元・grep）は、すべて head のリビジョンで読む。ワークツリーを信用しない — マージ済みPRを後続ブランチ上で解説すると、「すでにあったもの」に後から入った変更が混ざり、読み手には検出できない。

- `headRefOid` で head の SHA を取り、`git rev-parse HEAD` と **SHAで**比較する。ブランチ名の一致で判定しない — 同名のローカルブランチが PR head より古いことは普通にある
- 一致 → そのまま Read / grep してよい
- 不一致 → ブランチを切り替えず、`git show "${OID}:<path>"` と `git grep <識別子> "$OID" -- .` で読む（`OID` は head の SHA）。
  **波括弧は必須。** zsh では `$OID:frontend/...` の `:f` が修飾子として食われ、`<sha>ontend/...` という壊れた引数になって失敗する（`:h` `:t` `:r` `:s` 等も同じ）
- オブジェクトが無い（`unknown revision` / `ambiguous argument` が出る）→ `git fetch origin refs/pull/<N>/head` してから同じ手順。**マージ済みPRのマージコミットや head ブランチはローカルに無いのが普通**で、`<merge>^2` はそのままでは解決できない
- クローンが無い → 上の `gh api .../contents?ref=<headRefOid>` で読む

`gh` が使えない（GitHub以外・未認証）場合は「ブランチ名」の行として扱い、PR本文の代わりに `git log <base>..<head>` のコミットメッセージを読む。

### 差分の外から集めるもの

差分だけ読んで組み立てた説明は、たいてい周囲の既存実装を誤読している。

- **PR本文** — 設計判断とその理由はここにしかないことが多く、コードからは復元できない。ただし **Botが生成した節**（CodeRabbit の Summary、自動リリースノート等）は人間の判断ではないので、「なぜこうなっているか」の根拠に引かない。人が書いた節だけを使う
- **触られたファイルの全体** — hunkだけ読むと、そのファイルが元々何をしていたか分からないまま差分を語ることになる
- **呼び出し元と呼び出し先** — 差分には現れないが、流れを繋ぐのに要る
- **関連コミット** — 特に「レビュー指摘の修正」系は、その設計の争点がどこだったかを教えてくれる
- **プロジェクトの規約** — CLAUDE.md / README / 設計ドキュメント

### リポジトリの規約と慣習

差分が「なぜその形なのか」の半分は、そのリポジトリの取り決めで決まっている。知らずに読むと、ごく普通の選択が奇妙に見えたり、逆に**重要な逸脱を見落とす**。

探す場所:

- `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` / `README`
- `ARCHITECTURE*.md` / `CODING_STANDARDS*.md` / `docs/` / ADR
- `.github/` のテンプレートとワークフロー — CIが何を必須にしているか
- lint・フォーマッタの設定（`.eslintrc` / `.rubocop.yml` 等）— 機械で強制されている部分
- **パッケージ／モジュールのドキュメントコメント** — `doc.go`、パッケージ冒頭のコメント、`__init__.py` の docstring。`CLAUDE.md` が無いリポジトリでは、規約がここにしか書かれていないことがよくある
- 近い既存実装そのもの。文書化されていない慣習は、模範となるファイルを読むしかない

拾うもの:

| 種類 | 例 |
|---|---|
| 層の分担 | どこに何を書き、何を書かないか |
| 命名とディレクトリ構造 | feature 単位か層単位か、バレルの有無 |
| 禁止事項 | 採用しないライブラリ、使ってはいけないコマンド、避ける書き方 |
| 模範ファイル | 「新しく書くときはこれに倣う」と明示されているもの |
| PR自体の制約 | 変更行数の上限、必須の検証コマンド、更新が要る仕様ファイル |

### ツアーが成立するか

Phase 1 に進む前に `git diff --stat` と `git diff -w -M --stat` を比べる。次のどれかに当たるなら計画を出さず、理由と代替を1段落で伝えて止まる:

- **変更40ファイル超、または +2000行超** — 「このPRには〈流れの一覧〉がある。どれを歩くか」を聞く。1本選んだら、残りは計画の「歩かない場所」に列挙する
- **`-w -M` で差分がほぼ消える**（リネーム・整形中心）— 振る舞いが変わっていないので、ツアーではなく変更カテゴリの箇条書きで終える
- **依存更新・CI・ドキュメント・テストのみ** — 同上
- **リバート** — 元PRを `gh pr view` で引き、「元PRが敷いた流れのどこが消えるか」として歩く。差分状態は「削除」

### Phase 0 を抜ける前の確認

計画を書き始める前に、6つとも済んでいるか数える。**飛ばしやすいのは規約の収集**で、ここを抜かすと「なぜこの形なのか」が全駅で薄くなる。

1. 対象のリポジトリと base / head を確定した
2. head のリビジョンを SHA で照合し、読む先を固定した
3. PR本文（人が書いた節）と関連コミットを読んだ
4. **リポジトリの規約と慣習を集めた**（`CLAUDE.md` が無くても、パッケージの doc コメント・CI・lint 設定のどれかにはある）
5. 敵対的レビューを起動した（または、使える `code-review` が無いと判断し、その理由を計画に書く準備ができた）
6. ツアーが成立することを確かめた

この段階では解説を始めない — 行程が立つ前に中身を語ると、後で出す計画と食い違う。何を読んでいるかを一言ずつ伝えるのは構わない（収集は長くかかるので、無言だと止まったように見える）。

## 敵対的レビューを併走させる

ツアーは「どう動くか」を説明するもので、良し悪しの判定はしない。ただし読み手にとって **その場所に既知の問題があるか** は理解の一部になる。そこで Phase 0 でレビューを1回だけ起動し、結果を駅ごとに配る。

**起動する前に、使える `code-review` がどれかを見分ける。** このツアーが前提にしているのは、effort レベル（`low` / `medium` / `high` …）と `--comment` / `--fix` フラグを受け取り、結果を手元に返す `code-review` スキルである。配布先の環境にそれがあるとは限らず、**同じ名前で別物が入っていることもある** — 公式マーケットプレースの `code-review` プラグインは、PR番号を受けて `gh pr comment` で GitHub にレビューコメントを**投稿する**。ツアーの途中でこちらが起動すると、解説のつもりで PR に公開コメントが付く。

- 利用可能なスキル一覧の `code-review` の説明文が、effort レベルと `--comment` / `--fix` に触れている → 下の手順で起動する
- それ以外（名前が無い、説明が「Code review a pull request」だけ、`code-review:code-review` のようにプラグイン名前空間付きでしか無い、判別できない）→ **起動しない**。レビュー併走を省いてツアーを続ける（→ 下の「レビューが走らないとき」）

迷ったら起動しない側に倒す。レビューが無くてもツアーは成立するが、誤って投稿されたコメントは取り消しても通知が残る。

**起動。** 対象が確定したら `code-review` スキルを **effort `high`** で起動する。ユーザーが effort を明示していればそれに従う。ツアー中に再実行しない — 1回の結果を全駅で使い回す。

**対象は head のブランチ名で渡す**（`high feat/orders-api`）。PR番号だけを渡すと `main...HEAD`、つまり**手元のブランチの差分**をレビューしてしまうことがある（実測）。ワークツリーが head と違うスタックドPRでは、隣のPRの変更まで混ざった結果が返る。ブランチ名が使えない場合でも、返ってきた結果の対象範囲を必ず読む。

**`--comment` も `--fix` も付けない。** ツアーのレビューは読み手に見せるためのもので、PRへの投稿でも修正でもない。同名の `/code-review` コマンドを提供するプラグインが入っている環境では、そちらが GitHub にレビューコメントを投稿してしまうことがある。**effort 付きで呼び、結果が手元に返ってくること**を確認する。投稿されたら黙って進めず、ユーザーに伝える。

**待たない。** `code-review` はフォークして**バックグラウンドで走る**（起動時に走っている旨だけが返り、結果は後から task notification で届く）。完了を待って計画提示を止めない。届いた時点から駅への割り当てを始め、届く前に通過してしまった駅の指摘は締めでまとめて出す。

ツアーが先に終わってしまうこともある。その場合は締めの「残る論点」に全件を合流させ、**まだ届いていないなら「レビューは未着」と書く** — 黙って省くと、読み手は指摘ゼロだったと受け取る。

**まず対象範囲を確認する。** 結果が届いたら、指摘を配る前に **レビューが実際にどの範囲を見たか** を確かめる。PR番号を渡しても、カレントのワークツリー差分（`main...HEAD`）をレビューしていることがある。**ワークツリーが head と違うとき**（スタックドPRの後続ブランチに立っている等）は、ツアーが読んでいる範囲とレビューが見た範囲が必ずずれる。

範囲がツアーの `base...head` と違ったら:

- **ツアーの差分に含まれない指摘を駅に配らない。** 「このPRの指摘」として出すと嘘になる
- 隣接PRに当たる指摘は、締めで「**このツアーの範囲外（隣のPRの指摘）**」として分けて出す。混ぜない
- 範囲がずれていた事実そのものを、締めで1行伝える

**割り当て。** 範囲内の各指摘の `file:line` を、その行を含む駅に配る。どの駅にも該当しないもの（差分外、全体設計に関するもの）は Phase 3 の「残る論点」へ回す。

**出し方。** 該当する駅に `### レビューでの指摘` を足し、1件ずつ「何が・どこで・確度（CONFIRMED / PLAUSIBLE）」だけを書く。結果に確度が付いていないこともある（実測）。その場合は確度を推測して書かず、最初に指摘を配る駅で「このレビュー結果には確度が付いていない」と一言伝える。**そこで深追いしない** — 修正方針の議論を始めるとツアーが止まる。直したくなったら、ツアーの後で effort 付きの `code-review` に `--fix` を付けて渡す、と案内して先へ進む（上の見分けで別物と判断した環境では案内しない）。

指摘が無い駅では節ごと省く。「指摘なし」とは書かない — 空の節が全駅に並ぶとツアー本体が薄まる。

**レビューが走らないとき**（スキルが無い・上の見分けで別物と判断した・対象が非対応・失敗）は、その旨を計画の時点で1行伝えてツアーを続ける。黙って省かない。このときツアー本体は何も変えない:

- 計画の **レビュー** 行に「併走なし（理由）」と書く
- 各駅の「レビューでの指摘」節はすべて省き、サイドバーの `⚠` も付けない
- 締めの「残る論点」に「レビューは併走させていない」と1行添える — 「未着」とも「指摘なし」とも書かない。読み手はそれぞれ違う意味に受け取る
- 代わりに自分で粗探しを始めない（→「守ること」）

## エントリーポイントの決め方

エントリーポイント = **外部からの刺激がこのシステムに入る最初の一点**。

| スタック | 典型的な起点 |
|---|---|
| HTTP API | ルータ定義 → ミドルウェア → ハンドラ |
| CLI | `main()` / コマンド定義 |
| フロント（SPA / SSR） | ルート・ページコンポーネント → データ取得 |
| UI イベント | イベントハンドラ（onSubmit / onClick / gesture）→ 状態更新 → 再描画 |
| モバイル | アプリ起動 / ディープリンク / 画面遷移 → ViewModel・Presenter |
| ワーカー / ジョブ | ジョブの登録側と、ワーカーのディスパッチ |
| 外部イベント | webhook / メッセージ購読 / cron のハンドラ登録箇所 |
| ライブラリ | 公開API（エクスポートされた関数・型） |
| スキーマ変更 | マイグレーションの適用と、その表を触る最初のクエリ |

## 歩き方を決める

**判定は「差分の外から差分へ到達できるか」で行い、根拠を file:line で示す。** 到達の形は3つ:

1. **直接呼び出し** — 非テストコードからの参照が `grep` で見つかる
2. **フレームワークの規約** — ファイルベースルーティング、`routes.rb` の `resources`、Manifest / plist 登録、DIコンテナのオートワイヤ、デコレータ・アノテーション。この場合は規約の根拠（設定ファイル・登録箇所）を起点にする
3. **どちらも無い** → 到達できない

`grep` だけで判定すると、規約で結線されるフレームワーク（Next.js のファイルルーティング、Rails のコントローラ、Spring の `@RestController`）で必ず誤判定する。誰も import していないのに、実際は繋がっている。

| | モードA: 経路をなぞる | モードB: 公開面から内へ降りる |
|---|---|---|
| 判定 | 差分の外から到達できる | 到達できない |
| 順路 | 入口 → 終端（実行順） | 起点で断線を確認 → 差分の公開面 → 内側 |
| 語る中心 | どこで判断が分かれるか | 何がまだ繋がっていないか |
| 図の主役 | 連続した線と、その分岐 | 線が途切れている位置 |

**モードA** では、リクエスト／コマンド／イベントを1本選び、入口から終端まで頭から追う。差分のない駅も飛ばさない — 経路が連続していることが読み手の地図になる。

**モードB** では、まずプロセスの本当の起点（サーバの起動と配線、アプリのエントリ、フレームワークのルート登録）から入り、**そこに今回の差分が居ないこと**を確認する。次に、差分のうち外から参照される（される予定の）**公開面**（インターフェース / 型 / export された関数 / コンポーネントの props / スキーマ）へ移り、依存の向きに沿って内側へ降りる。

**混在は普通にある。** 経路が途中まで繋がり、その先の差分がまだ誰からも呼ばれていない、という形。繋がっている区間はモードAで歩き、届いていない差分は断線マーカーの先に置く。1本のツアーで両方を使ってよい。到達性は駅ごとに確かめる — 入口が繋がっているからといって、終点まで繋がっているとは限らない。

「モードA/B」は内部用語なので、読み手には出さない。

## 実行順と依存順がずれるとき

流れの順に歩いていると、**後の駅で足された値や型を、前の駅がすでに使っている**場面に出会う。矛盾ではなく、PRが「先に使う側を書き、後から供給側を足した」ことの現れで、フルスタックのPRでは頻繁に起きる（画面側が使うフィールドを、最後にサーバのレスポンスへ追加する等）。

扱い方:

1. 前の駅では、その値が **このPRで足されたもの** だとその場で明記し、供給元の駅番号を指す（「この `discountId` は Step 6 で追加された値」）
2. 供給元の駅に着いたら回収する（「Step 2 の判定が成立するのは、この1行のおかげ」）
3. 図では、戻り矢印のラベルか `Note` に書く（シーケンス図なら戻り値の矢印がちょうどその位置にある）。図の外の注記に逃がさない

この往復は、そのPRで一番説明が要る場所であることが多い。差分を上から順に読んだ人が必ず取りこぼすのが、まさにこの依存だから。

## Phase 1: 計画提示

チャットにこの形で出す:

```markdown
## ツアー計画: <PRタイトル>

**一言で**: <このPRが何を可能にしたか。1〜2文>
**範囲**: `<base>` → `<head>` / <N>ファイル / +<追加> -<削除>
**起点**: `<file:line>` — <なぜここを起点に選んだか>
**歩き方**: <「リクエスト1本を入口から終端まで追う」／「線路が途切れている場所を確認してから、公開面 → 内側へ降りる」>
**歩かない場所**: <このPRに含まれるが今回の順路から外す変更と理由。無ければ「なし」>
**レビュー**: <敵対的レビューを high で併走中。結果は該当する駅で触れる／走らせられない場合はその理由>

| # | 立ち寄り先 | 見どころ | 差分 |
|---|---|---|---|
| 1 | `path/to/x.go` | <一言> | 既存のみ |
| 2 | `path/to/y.sql` | <一言> | 🆕 新規 |
| 3 | `path/to/z.go` | <一言> | ✏️ 変更 |

**図解**: 全体マップをアーティファクトで公開しました（ステップごとに現在地を更新します）
```

ステップは **3〜7個**。それ以上に割れるなら粒度が細かすぎる — ファイル単位ではなく「流れの関節」単位で切る。

**同型の反復は1駅に畳む。** 同じ変更が複数ファイルに散る区間（prop を4つの描画先へ通す、同じ引数を全実装に足す等）は、1駅にまとめて「同じ形の変更が N ファイル」と述べ、代表1ファイルだけ引用する。ファイル数だけ駅を作ると、行程の見た目が実際の関節の数と合わなくなる。

計画を出したらマップのアーティファクトを公開し（→ `references/tour-map.md`）、「Step 1 から始めますか？」で **止まる**。

## Phase 2: ステップ実行

1ステップ = 1ターン。チャットでこの形を使う:

```markdown
## Step <N>/<総数>: <見出し>

📍 `path/to/file.go:120-160`

### すでにあったもの
<このコードが元々何をしていたか。この差分がなくても成立していた部分。
 レイヤの役割、既存の規約、周囲との関係。>

### このPRでの差分
<入口の関数から1ホップずつ番号を振った「呼び出し順のトレース」を骨格にする（下の説明）。
 コード引用はそのホップの中に置き、判断の核心の行だけに絞る>

### このリポジトリの約束事
<この駅のコードが従っている取り決めと、その出典（`CLAUDE.md` の該当見出し、
 `CODING_STANDARDS.md`、模範ファイルの指定など）。
 逸脱しているならそれも書く — 逸脱はたいてい意図的な判断で、説明する価値がある。>

### なぜこうなっているか
<PR本文の設計判断、レビューでの争点、代替案が落とされた理由。
 差分を見ただけでは分からない部分をここに置く。>

### レビューでの指摘
<併走させた code-review が、この駅の行に対して出した指摘。1件ずつ短く。
 何が・どこで・確度。該当が無ければこの節ごと省く。>

### 次の行き先
<`path/to/next.ts:40` — 何がどう渡るか。呼び出しで進むとは限らない。
 UIでは state を親へ上げ prop で子へ降ろすので、↑親へ / ↓子へ と運ばれるものを書く>

---
Step <N>/<総数> 完了。次は「<次の見出し>」です。「次」で進みます。
```

最終ステップだけ末尾を差し替える: `Step <総数>/<総数> 完了。全駅を回りました。「締め」で振り返りに入ります。`

「すでにあったもの」と「このPRでの差分」を必ず別見出しにする。混ぜると、読み手は**どこまでが今回の責任範囲か**を判断できなくなる。差分が一切ない駅では「差分」節に「このPRでは変更なし（流れを繋ぐために通過）」と書く。

**分岐のある駅では、全分岐をその場で列挙する。** 条件とそれぞれの行き先を出してから、このPRが選んだ道とその理由を示す。分岐は「どちらでも動くが、こちらを選んだ」という判断が露出している場所で、差分を読むだけでは選ばれなかった道が見えない。

**「このPRでの差分」は呼び出し順のトレースで書く。** 変更点を箇条書きで並べると、読み手は「コードのどこから始まり、何が何を呼んでいるのか」を自分で組み立て直すことになる。入口の関数から1ホップずつ番号を振る:

```markdown
① `Update` orders.go:56 — 入口。`userID` と `*Order` を受け取る
② → `marshalItems` orders.go:112 — Items を JSON に。nil は空配列に倒す
③ → `r.q(ctx)` base.go:28 — ctx にトランザクションがあればそれ、無ければプール
④ → `UpdateOrder`（生成コード）orders.sql.go:107 — `UPDATE … RETURNING *`
⑤ 戻り値で分岐
   ⑤-a 制約違反 → `orderConstraintErr` :98 → ドメインエラー
   ⑤-b 0行 → `notFoundOrWrap` base.go:38 → `ErrNotFound`
   ⑤-c 成功 → `toDomainOrder` :135 → `*domain.Order`
```

- 各ホップに **呼ぶ側の行 → 呼ばれる側の定義行** と、渡すもの・返るものを書く
- 番号は駅の図（呼び出し順の `sequenceDiagram` の `autonumber`）と揃える。本文と図を行き来できるようにするため
- 同じ道の短い版になっている兄弟メソッド（`Get` が `Update` の ③④⑤ だけを通る等）は、ホップを繰り返さず「どのメソッドがどの番号を通るか」の表にまとめる

長さの目安は **スクロールせずに読める量**。超えるならステップを割る。

解説し終えたら図を更新し、止まる。**過去の駅のパネルは消さない** — アーティファクトのサイドバーから読み手がいつでも戻れるようにしておく。

### 順路から外れたとき

- **停車中の質問には現在地を動かさず答える。** マップは publish しない。回答の末尾に「Step N/M で停車中。「次」で進みます」を添える。
- **停車中に「レビューの指摘を検討して」と言われたら、対象は現在の駅に配った指摘だけ。** ツアー全体の指摘を検討し始めない — 停車中の「指摘」は、いま画面にある指摘を指している。全体を見たいと言われたときだけ範囲を広げる。
- **飛ばし・戻り。** 現在地は常に1つ。飛ばした駅は未訪問のまま残す（通っていないのに訪問済にすると嘘になる）。戻ったときも、先の駅の訪問済は消さない。
- **別セッションからの再開。** スクラッチパッドはセッション固有なので、同じファイルパスでの再publishは効かない。Phase 1 の返答に残したアーティファクトURLを使い、`action:"read"` で内容を取り戻してから `url` 付きで publish する。URLが分からなければ `action:"list"` で探す（そのためにタイトルは変えない）。

## Phase 3: 締め

最終ステップの**次のターン**。マップは進捗を「完了」にし、全駅を訪問済・現在地なしにして最後に1回 publish する。チャットはこの形:

```markdown
## ツアー完了: <PRタイトル>

**できるようになったこと**: <Phase 1 の「一言で」への答え合わせ>
**まだ繋がっていない先**: <断線の先。次のPRが埋める場所を file:line で>
**残る論点**: <設計上まだ決着していないこと、テストが担保していない範囲。無ければ「なし」>
```

## 守ること

- **憶測で流れを繋がない。** 到達性は上の3形で実際に確かめ、根拠を file:line で示す。辿れなかったら「ここから先はまだ実装がない」と書く。存在しないハンドラを捏造して線を繋ぐのが、このツアーで一番やってはいけないこと。
- **ツアー自身はレビューをしない。** 良し悪しの判定は併走させた `code-review` に任せ、その結果を駅ごとに配るだけに留める。自分で粗探しを始めるとツアーが止まる。歩く中で明らかな破綻に気づいた場合だけ1行添える。
- **生成コードは1ノードとして通過する。** ORMクライアント、APIクライアント、protobuf、その他 codegen 出力は逐行解説せず、「この定義から何が生成され、どこで使われるか」だけ示す。
- **テストは仕様の証拠として引く。** 駅の中で「この振る舞いは `TestXxx` が担保している」と添える程度に。テスト単独の駅は、テストが設計の争点そのものを示している場合に限る。
- **規約は出典付きで引く。** 「一般にこうする」ではなく「このリポジトリの `CLAUDE.md` がこう決めている」と言えるものだけを約束事として出す。一般論と混ぜると、読み手はどこまでがこのチームの決まりなのか分からなくなる。出典が示せない慣習は「既存実装がそう書いている」と事実として述べる。
- **専門用語は初出時に一言で開く。** ただし説明のための説明を積み上げない。

## 図解

**毎ステップ、図を2枚並べて載せる。** ツアー全体の図を常設し、その下にステップ固有の図を2枚置く: (a) 呼び出し順の `sequenceDiagram`（`autonumber` で本文のトレース ①②… と番号を揃える）と、(b) 戻り値・条件による分岐の `flowchart`（ノードに file:line）。どちらか一方に置き換えない — 順番と分岐は1枚に押し込むとどちらも読めなくなる。差分が無く通過するだけの駅では省いてよい。

**全体図の形は歩き方で変わる。** 経路をなぞるモードなら `sequenceDiagram`（誰が誰を、どの順で呼ぶか）。公開面から降りるモードでは呼び出しの列が存在しないので、**層と断線を描く `flowchart`** にする。後者では下りの呼び出しよりも、**DBやライブラリから上がってくるエラーをどう翻訳するか**が主役になることが多い — その戻りの矢印を省かない。図式は目的で選ぶ — 順序とやり取りならシーケンス図、条件分岐ならフローチャート、状態遷移なら状態図、データ構造なら ER 図。箱を縦に並べただけの行程表は図ではない。

描画は mermaid（アーティファクトがネイティブに描画する。ライブラリは読み込まない）。構成・現在地の示し方・再publishの手順は `references/tour-map.md` を読む。最初のアーティファクトを書く前に必ず読むこと — 1枚を段階更新する設計で、初回の作りを間違えると後続ステップで破綻する。

Artifact ツールが無い環境では、同じHTMLをローカルファイルに書き出して代える（手順は `references/tour-map.md` の「Artifact ツールが無い環境」）。図を諦めてチャットに描くことはしない。
