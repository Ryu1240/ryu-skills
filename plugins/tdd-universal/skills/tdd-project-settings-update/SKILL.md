tdd-universal の全 TDD スキル（tdd / tdd-red / tdd-green / tdd-refactor / tdd-commit / tdd-coverage-review / tdd-optimize / tdd-evacuator / tdd-workflow-update）が参照する単一情報源 `.claude/skills/_shared-tdd/project-settings.md` を、自然言語の指示から安全に更新する。

汎用版ではこのファイルが言語知識のすべて（テスト実行コマンド・配置/命名・独立性の担保方法・言語固有の慣習）を保持している。初回生成は `tdd-bootstrap`、このスキルは生成済み設定の恒常的な微調整・追記・修正を担う（`tdd-bootstrap --force` の再生成と違い、手編集を潰さず差分だけを当てる）。

このファイルへの誤った編集は全 TDD フェーズの挙動に一斉に波及する。だから「diff 提案 → 承認 → 適用 → 検証 → メモリ同期」の順を守る。

## 前提チェック

1. 指示（`$ARGUMENTS`）が非空。空なら「何を変更しますか？」と確認して中断。
2. カレントリポジトリに `.claude/skills/_shared-tdd/project-settings.md` が存在する。無ければ「まだ bootstrap されていません。`/tdd-bootstrap` で生成してください」と案内して中断。
3. ファイルに `{{` プレースホルダが大量に残っている（未 bootstrap 同然）→ 個別修正より `/tdd-bootstrap` の方が適切と案内し、続行可否を確認。

## Step 1: 現状読込

`.claude/skills/_shared-tdd/project-settings.md` を全文 Read し、セクション構成（スタック / テスト実行コマンド / テスト配置と命名規則 / テストデータ・外部依存 / 独立性の担保方法 / 言語固有の慣習 / CI・hook / 不変条件 / ブランチ・コミット）を把握する。指示内容と矛盾・重複する既存記載がないかをこの時点で洗い出す。

## Step 2: diff 提案

指示を解釈し、編集操作を組み立てて適用前に提示する:

- 追記: 既存セクションに収まるなら既存セクションへ。新概念のみ新セクション。このファイルは全 TDD スキルのコンテキストに毎回ロードされるため、肥大化はコスト。冗長な説明より簡潔な事実+理由の一行を優先する。
- 修正: 対象箇所の before/after を明示。
- 削除: 削除理由と、削除によって挙動が変わる TDD スキル・フェーズを一言添える。
- 書式: 既存の書式に合わせる。プレースホルダ（`{path}`/`{case}`/`{line}`）の規約を崩さない。
- 矛盾検出: 既存記載と衝突する場合は上書きか併記かを提案に含める。

### 特別扱いが必要なセクション

- テスト実行コマンド: ここが誤ると全フェーズが空振りする。変更時は、そのコマンドが実在するか（スクリプト定義・Makefile ターゲット等）を Grep/Read で裏取りしてから提案する。裏取りできなければ「未検証」と明示して承認を求める。
- ⚠️ 不変条件: 「不変条件（全スキル共通・破ってはいけない線）」への追加・変更・削除は、品質ガードレール（1サイクル=1テスト=1コミット、テスト独立性、既存慣習の踏襲）の変更を意味する。diff 提案時にその旨を⚠️付きで明示し、影響（どのスキルのどの判断が変わるか）を説明したうえで、通常の承認とは別に変更意図を再確認する。
- 独立性の担保方法 / 言語固有の慣習: Red・Refactor・Optimize の判断に直接効く。変更が既存テストの実態と整合するか、既存テストを1件 Read して確認したうえで提案する。

## Step 3: 承認ゲート（必須）

AskUserQuestion で `[適用] / [キャンセル] / [部分適用]` を確認。[適用] のときのみ Step 4 へ。[部分適用] は変更単位ごとに採否を再質問。[キャンセル] は何も書かずに終了。

## Step 4: 適用と検証

1. Edit で承認済みの変更のみ適用。承認していない箇所には触れない。
2. `git diff -- .claude/skills/_shared-tdd/project-settings.md` で実際の差分を提示し、提案どおりか確認する。
3. `{{` を新たに持ち込んでいないことを Read で確認（プレースホルダが残ると `/tdd` の Phase 0 が止まる）。
4. コミットはしない。変更は working tree に残し、コミット判断はユーザーに委ねる（明示的に指示された場合のみコミット）。

## Step 5: 永続メモリとの同期提案（任意・メモリ機能が有効な場合のみ）

このスキルはリポジトリ配置でチーム共有される。実行者が永続メモリ機能を使っている場合に限り、project-settings.md の運用知識と重複・矛盾するメモリがないか確認する。メモリディレクトリが存在しない実行環境ではこの Step をスキップし、Step 6 へ進む（他メンバーの環境ではメモリが無いのが普通）。

システムプロンプトにメモリディレクトリ（MEMORY.md がインデックス）が示されている場合:
- 今回の変更と矛盾または重複する既存メモリを Grep で探す（例: テストコマンド名 / ランナー名 / lint / 言語名で検索）。
- 矛盾するメモリが見つかったら、同期更新案（メモリ本文と MEMORY.md のインデックス行）を提示し、承認後に更新する。
- 見つからなければ「メモリ同期不要」と報告するだけでよい。新規メモリの作成はユーザーが求めた場合のみ。

## Step 6: 完了サマリ

変更したセクション / 保護した箇所（触れなかった不変条件等）/ コマンドの裏取り結果 / メモリ同期の有無 / 「コミットは未実施（working tree に差分あり）」を簡潔に報告する。
